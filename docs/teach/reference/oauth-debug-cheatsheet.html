Шпаргалка: отладка OAuth в Supabase

Одна страница на случай «не работает». Диагностика по симптому, а не по гаданию. Печатать и держать рядом.

1 Флоу в одну строку

клик → /auth/v1/authorize (flow_state + challenge)
     → accounts.google.com (человек)
     → /auth/v1/callback (Supabase: google code → tokens → user + identity)
     → твой /auth/callback?code=… (exchangeCodeForSession: code + verifier из cookie)
     → cookie сессии → редирект

Правило локализации бага: смотри, на каком домене остановился браузер. Застрял на accounts.google.com — виновата настройка Google Cloud. На <ref>.supabase.co — настройки провайдера или allow list в Supabase. На localhost — твой код.

2 Четыре адреса, которые нельзя путать

ЧтоЗначение для anihive
Google Cloud → Authorized redirect URIhttps://<ref>.supabase.co/auth/v1/callback
Google Cloud → Authorized JavaScript originНе нужен для этого флоу (нужен только для One Tap / клиентского SDK Google)
Supabase → Redirect URLs (allow list)http://localhost:3000/** + https://<прод-домен>/**
Supabase → Site URLПрод-домен. Это fallback: сюда улетают все redirectTo, не прошедшие allow list
Твой код → options.redirectTo${window.location.origin}/auth/callback

3 Симптом → причина → лечение

СимптомПричинаЛечение
Google показывает ошибку про несовпадение redirect URI (redirect_uri_mismatch) Google сверяет адрес побайтово. Лишний слэш, http вместо https, другой project ref Скопировать URL из Supabase → Providers → Google и вставить в Google Cloud без правок
Google говорит про неверный клиент (invalid_client) Client ID / Secret в настройках провайдера Supabase не от того OAuth-клиента Перевыпустить secret и вставить заново; проверить, что клиент типа «Web application»
Вернулся с ?error=access_denied Человек нажал «Отмена» на экране согласия. Это не баг Обработать в route handler: редирект на /login с нейтральным сообщением
Ошибка про пустой code verifier (текст обычно содержит code verifier и non-empty) Код есть, cookie …-code-verifier нет: флоу начат в другом браузере/инкогнито, cookie почищена, либо обмен идёт из контекста без доступа к тем же cookie Начать вход заново в том же окне; проверить в DevTools, что cookie появляется сразу после клика
Ошибка про flow state (invalid flow state / expired) Запись auth.flow_state уже использована или истекла. Классика: перезагрузка страницы callback, повторный обмен того же кода, кнопка «назад» Не переиспользовать код; после успеха всегда редиректить (чтобы reload не попал повторно на обмен)
С прода выкидывает на localhost:3000 redirectTo не прошёл allow list → сработал Site URL Добавить прод-домен в Redirect URLs; поменять Site URL на прод
404 на своём /auth/callback next-intl в src/proxy.ts переписал/отредиректил путь на локализованный Исключить auth из config.matcher (см. урок 1, ловушка 2)
Обмен прошёл, но UI считает, что гость Cookie поставлена, но клиентский стор её не прочитал Убедиться, что возврат — полная навигация (не router.push внутри SPA); useSessionSync читает сессию при монтировании
Сессия исчезает через час Refresh не происходит: middleware не обновляет сессию на этом пути Проверить, что updateSession вызывается для обычных страниц (исключение из matcher — только для /auth)
Вошёл через Google — попал в другой аккаунт, чем с паролем Identity linking не сработал: email у провайдера не подтверждён или отключено связывание Тема урока 3. Быстрая проверка — запрос к auth.identities ниже

4 Инструменты

DevTools

  • Network → Preserve log — обязательно. Без него цепочка 302 исчезнет при навигации, и ты не увидишь, где именно всё сломалось.
  • Application → Cookies → localhost:3000. Ожидаемая картина: после клика появляется sb-<ref>-auth-token-code-verifier; после обмена она исчезает, а появляется sb-<ref>-auth-token (иногда чанками .0, .1).
  • Полный сброс состояния перед тестом: Application → Storage → Clear site data. Дешевле, чем отлаживать призрачную сессию.

SQL в Supabase Studio

-- кто вошёл и чем
select u.id, u.email, u.last_sign_in_at, i.provider, i.provider_id
from auth.users u
join auth.identities i on i.user_id = u.id
order by u.created_at desc
limit 10;

-- незавершённые попытки входа (диагностика flow state)
select id, provider_type, authentication_method, created_at
from auth.flow_state
order by created_at desc
limit 10;

Логи

  • Supabase Dashboard → Logs → Auth Logs: там видно отказ на стороне GoTrue с настоящей причиной, а не обобщённое сообщение, которое доехало до браузера.

5 Что проверить перед тем, как спрашивать

  • Флоу начат и завершён в одном окне, без инкогнито и без смены браузера.
  • Cookie …-code-verifier реально появлялась после клика.
  • Код обменивается ровно один раз (в консоли нет двух запросов grant_type=pkce).
  • Оба списка адресов (Google Cloud и Supabase) содержат нужные URL — они разные.
  • Auth Logs в дашборде прочитаны: там точная причина.
