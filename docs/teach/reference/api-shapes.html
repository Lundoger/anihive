Формы данных: что вызываешь и что получаешь

Точные типы и конкретные значения для двух функций, на которых держится весь OAuth-флоу. Всё проверено по node_modules этого проекта, версия @supabase/auth-js 2.87.1.

1 signInWithOAuth

Что принимает

@supabase/auth-js/dist/module/lib/types.d.ts:476

type SignInWithOAuthCredentials = {
  provider: Provider;              // 'google' | 'discord' | 'github' | …
  options?: {
    redirectTo?: string;           // куда Supabase вернёт браузер (шаг 4)
    scopes?: string;               // через пробел: 'email profile'
    queryParams?: { [key: string]: string };
    skipBrowserRedirect?: boolean; // не уводить страницу самому
  };
};

Что возвращает

@supabase/auth-js/dist/module/lib/types.d.ts:135

type OAuthResponse =
  | { data: { provider: Provider; url: string }; error: null }
  | { data: { provider: Provider; url: null  }; error: AuthError };

Никакой сессии здесь нет и быть не может. Сессия появится только на шаге 5, после обмена кода. Всё, что отдаёт эта функция, — адрес, по которому надо уйти.

Что она делает внутри (важно: ни одного сетевого запроса)

GoTrueClient.js:1837 — _handleProviderSignIn

async _handleProviderSignIn(provider, options) {
    const url = await this._getUrlForProvider(`${this.url}/authorize`, provider, {
        redirectTo: options.redirectTo,
        scopes: options.scopes,
        queryParams: options.queryParams,
    });
    // try to open on the browser
    if (isBrowser() && !options.skipBrowserRedirect) {
        window.location.assign(url);
    }
    return { data: { provider, url }, error: null };
}

Четыре шага, все локальные:

  1. сгенерировать code_verifier и записать его в storage (у нас — в cookie);
  2. посчитать code_challenge;
  3. склеить строку URL на /auth/v1/authorize — никакого fetch;
  4. если это браузер и не сказано обратное — window.location.assign(url).
Отсюда сразу два следствия

a) На сервере isBrowser() ложно, значит редиректа не будет — функция вернёт data.url и замолчит. Если ты его не используешь, не произойдёт ничего, кроме постановки cookie с верификатором.
b) Запись flow_state в базе создаётся не здесь, а когда браузер реально придёт на /authorize. До навигации на сервере Supabase не знает о попытке входа.

Значения на практике

// вызов
const result = await getBrowserClient().auth.signInWithOAuth({
  provider: "google",
  options: { redirectTo: "http://localhost:3000/auth/callback?next=%2Fsettings" },
});

// result, если всё хорошо (но эту строку ты почти никогда не увидишь:
// страница уже уходит на Google)
{
  data: {
    provider: "google",
    url: "https://abcdefgh.supabase.co/auth/v1/authorize"
       + "?provider=google"
       + "&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM"
       + "&code_challenge_method=s256"
       + "&redirect_to=http%3A%2F%2Flocalhost%3A3000%2Fauth%2Fcallback%3Fnext%3D%252Fsettings"
  },
  error: null
}

// result, если провайдер выключен в дашборде
{
  data: { provider: "google", url: null },
  error: AuthError { message: "Unsupported provider: provider is not enabled", status: 400 }
}

Обрати внимание на двойное кодирование next: сначала он внутри своего redirectTo, потом весь redirectTo кодируется как query-параметр. Собирай URL через URL и URLSearchParams, а не конкатенацией строк.

2 exchangeCodeForSession

exchangeCodeForSession(authCode: string): Promise<AuthTokenResponse>

// то есть, в развёрнутом виде:
| { data: { user: User; session: Session }; error: null }
| { data: { user: null; session: null };    error: AuthError }

Что происходит внутри (GoTrueClient.js:764):

const storageItem = await getItemAsync(this.storage, `${this.storageKey}-code-verifier`);
const [codeVerifier, redirectType] = (storageItem ?? '').split('/');

await _request(this.fetch, 'POST', `${this.url}/token?grant_type=pkce`, {
  body: { auth_code: authCode, code_verifier: codeVerifier },
});

await removeItemAsync(this.storage, `${this.storageKey}-code-verifier`);  // одноразовый
await this._saveSession(data.session);                                    // пишет cookie
await this._notifyAllSubscribers('SIGNED_IN', data.session);

Ключевое: верификатор берётся из storage, а не из аргумента. Ты передаёшь только code — вторую половину пары клиент находит сам. Именно поэтому обмен обязан идти клиентом, у которого есть доступ к тем же cookie, что и у клиента, начавшего вход.

Форма Session — что реально приходит

{
  access_token: "eyJhbGciOi…",        // JWT Supabase, ~1 час, это его читает RLS
  refresh_token: "v1.MRq…",           // одноразовый, меняется при каждом refresh
  expires_in: 3600,
  expires_at: 1774020000,
  token_type: "bearer",

  provider_token: "ya29.a0Af…",       // ← токен GOOGLE, только сразу после входа
  provider_refresh_token: null,       // ← Google даёт только при access_type=offline

  user: {
    id: "8f14e45f-ea3d-4b1e-9c7a-2b0d5c1a9f33",
    email: "bohdan@example.com",
    app_metadata:  { provider: "google", providers: ["email", "google"] },
    user_metadata: { full_name: "Bohdan", avatar_url: "https://lh3.googleusercontent.com/…",
                     email_verified: true, sub: "1179271…" },
    identities: [ /* по одной записи на провайдера */ ],
  },
}
Ловушка на будущее

provider_token Supabase не хранит. Он есть в объекте сессии сразу после обмена и исчезает при следующем refresh. Нужен доступ к Google API от имени пользователя — сохраняй его сам в этот момент. Не нужен — просто игнорируй; для «войти и узнать, кто это» он не требуется.

Что не так с user_metadata

user_metadata заполняется из данных провайдера и перезаписывается пользователем через updateUser({ data }) — то есть это не доверенный источник. Для проверок прав используй app_metadata (его меняет только сервер) или свою таблицу profiles, как ты уже и делаешь.
