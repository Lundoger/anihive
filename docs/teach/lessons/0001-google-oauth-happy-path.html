Урок 1 · anihive · Google OAuth

Танец редиректов: от клика до cookie

Пять прыжков, один секрет в cookie и три ловушки, которые ждут именно в твоём проекте. К концу урока «Войти через Google» работает по-настоящему.

Твой LoginPage уже врёт пользователю. В messages/en.json лежит строка login.socialDescription — «You can also login with your social accounts» — и она рендерится на странице. Кнопок нет. Закроем разрыв, но не копипастой: сначала модель того, что происходит, потому что отлаживать ты будешь именно её, а не код.

1 Чем OAuth-вход структурно отличается от signInWithPassword

Именно поэтому обмен кода живёт в route handler, а не в server action: server action вызывается твоим кодом, а сюда браузер приходит сам, обычной GET-навигацией с чужого домена.

Ты уже написал serverSignIn. Там всё под твоим контролем: форма → server action → один fetch в Supabase → cookie. Один процесс, одно ожидание промиса, ошибка возвращается как значение.

OAuth ломает эту модель в одном месте, и всё остальное — следствия. Пароль пользователя тебе показывать нельзя, поэтому браузер уходит на чужой домен и возвращается сам. Нет промиса, который можно «подождать»: есть цепочка HTTP-редиректов, и твоё приложение получает управление лишь дважды — когда отправляет человека и когда принимает его назад. Всё, что нужно пронести между этими моментами, обязано лежать где-то — не в памяти JS, потому что страница за это время умрёт.

Главная мысль

OAuth — это не «способ проверить пароль». Это протокол выдачи одноразового талона третьей стороной, плюс задача «донести секрет через смерть страницы». Все ошибки — либо про неправильно зарегистрированный адрес возврата, либо про потерянный секрет.

2 Пять прыжков

Ниже — реальный путь для anihive в dev. <ref> — project ref из твоего NEXT_PUBLIC_SUPABASE_URL. Обрати внимание, что Google-код и Supabase-код — это два разных кода, и до твоего приложения доезжает только второй.

  1. Браузер · твой код Клик по кнопке. signInWithOAuth генерирует code_verifier, считает code_challenge = base64url(sha256(verifier)), кладёт verifier в cookie и уводит страницу через window.location.assign(url). GET https://<ref>.supabase.co/auth/v1/authorize?provider=google&code_challenge=…&code_challenge_method=s256&redirect_to=http://localhost:3000/auth/callback
  2. Supabase /authorize Создаёт запись flow_state: твой challenge, провайдер и redirect_to как referrer. Отвечает 302 на Google, подставляя свой client_id и свой адрес возврата. Id записи flow_state едет как state. 302 → https://accounts.google.com/o/oauth2/auth?client_id=…&redirect_uri=https://<ref>.supabase.co/auth/v1/callback&state=…&scope=email profile
  3. Google Логин и экран согласия — единственный шаг, где участвует человек. Дальше 302 назад, строго на тот адрес, который зарегистрирован в Google Cloud. 302 → https://<ref>.supabase.co/auth/v1/callback?code=<google_code>&state=…
  4. Supabase /callback Обменивает google_code на токены Google (уже своим client secret), проверяет подпись id_token, находит или создаёт запись в auth.users и auth.identities, выпускает свой одноразовый код и отдаёт его на тот redirect_to, который запомнил на шаге 2. 302 → http://localhost:3000/auth/callback?code=<supabase_auth_code>
  5. Браузер → твой route handler exchangeCodeForSession(code). Клиент достаёт code_verifier из cookie, отправляет пару «код + верификатор», получает сессию и пишет cookie сессии в ответ. Ты отвечаешь редиректом на нужную страницу. POST https://<ref>.supabase.co/auth/v1/token?grant_type=pkce → { auth_code, code_verifier }

Шаги 1 и 5 проверены по исходнику в твоём node_modules: @supabase/auth-js/dist/main/GoTrueClient.js — signInWithOAuth (~стр. 487), _handleProviderSignIn (~1837), _exchangeCodeForSession (~764). Шаги 2 и 4 — по Go-исходнику сервера: internal/api/external.go.

Побочный вывод, который стоит денег на отладке

PKCE здесь два. Внешний (шаги 2–4, между Supabase и Google) Supabase ведёт сам, его верификатор хранится в таблице oauth_client_state на сервере. Внутренний (шаги 1 и 5, между твоим браузером и Supabase) — твоя ответственность, его верификатор лежит в cookie. Когда ловишь invalid flow state или code verifier should be non-empty — речь всегда про внутренний.

3 Почему верификатор в cookie, а не в localStorage

Проверь сам: grep -n "flowType" node_modules/@supabase/ssr/dist/main/createBrowserClient.js

Обмен кода (шаг 5) делает сервер. Значит, серверу нужен доступ к верификатору, который сгенерировал браузер. localStorage сервер не видит — cookie видит. Поэтому @supabase/ssr подменяет storage у auth-клиента на cookie-хранилище, и в его исходнике есть отдельный костыль ровно под этот случай:

node_modules/@supabase/ssr/dist/main/cookies.js:263

// We don't have an `onAuthStateChange` event that can let us know that
// the PKCE code verifier is being set. Therefore, if we see it being
// set, we need to apply the storage (call `setAll` so the cookie is
// set properly).
if (key.endsWith("-code-verifier")) { … }

Отсюда два факта, которые полезно помнить наизусть:

  • createBrowserClient и createServerClient из @supabase/ssr жёстко задают flowType: "pkce" — не опция, а константа в коде библиотеки. Ты уже используешь PKCE, просто до сих пор он был не нужен.
  • Cookie называется sb-<ref>-auth-token-code-verifier. Она появляется в момент клика и исчезает после успешного обмена. Это твой главный диагностический признак в DevTools → Application → Cookies.
Прежде чем читать дальше: почему одноразовый code в адресной строке — это нормально?

Потому что кода недостаточно. Он бесполезен без code_verifier, который никогда не путешествовал по URL: он лежит в cookie на localhost:3000 и уходит на сервер один раз, в теле POST-запроса. Перехватчик URL получает половину пары. Ровно это и есть смысл PKCE — и причина, по которой implicit flow (токены прямо в URL) объявлен устаревшим.

4 Три ловушки конкретно в anihive

Ловушка 1: два разных «callback URL», которые все путают

Где настраивается Что вписать Кто это читает
Google Cloud → Authorized redirect URIs https://<ref>.supabase.co/auth/v1/callback Google на шаге 3. Сверяет побайтово → redirect_uri_mismatch.
Supabase → Auth → URL Configuration → Redirect URLs http://localhost:3000/** и прод-домен Supabase на шаге 4, чтобы решить, доверять ли твоему redirectTo.
Твой код, options.redirectTo ${origin}/auth/callback Supabase на шаге 2 (запоминает) и шаге 4 (редиректит).

Google про localhost:3000 вообще не знает и знать не должен — с его точки зрения клиент один: твой Supabase-проект. Если redirectTo не проходит allow list, Supabase молча отправит человека на Site URL. Симптом: «почему с прода меня выкинуло на localhost».

Ловушка 2: src/proxy.ts съест твой callback

Проверено по исходнику next-intl/dist/esm/development/middleware/middleware.js: у пользователя с локалью en будет rewrite на /en/auth/callback, у пользователя с ua — redirect на /ua/auth/callback. Обе ветки заканчиваются 404.

Твой matcher исключает api, _next/*, favicon.ico, img, .well-known. Путь /auth/callback под исключения не попадает — значит, до route handler'а первым доберётся handleI18nRouting. При localePrefix: "as-needed" next-intl перепишет непрефиксованный путь в /en/auth/callback, а такого роута у тебя нет: файл будет лежать вне сегмента [locale]. Итог — 404 вместо входа, причём код от Supabase уже сгорел (он одноразовый), и повтор ничего не даст.

Варианты решения — выбери и обоснуй в ревью:

  1. Исключить auth из matcher. Один callback-URL на все локали, короткий allow list. Минус: updateSession на этом пути не работает — но там он и не нужен, route handler сам себе клиент.
  2. Положить route внутрь [locale]. Локаль сохраняется бесплатно, но адресов возврата становится столько, сколько локалей, и все нужно держать в allow list.

Ловушка 3: после OAuth syncSessionFromServer() не нужен

В LoginForm ты вызываешь syncSessionFromServer(), и комментарий в коде объясняет почему: server action меняет cookie на сервере, браузерный клиент об этом не узнаёт. В OAuth-флоу возврат из route handler'а — это полная навигация документа. Приложение поднимается заново, useSessionSync при монтировании делает getSession() и читает свежую cookie. Ручная синхронизация здесь — лишний код. Понять, почему в одном случае нужна, а в другом нет, — и есть цель этого пункта.

6 Проверь себя

Какой URL вписывается в Google Cloud как Authorized redirect URI?

Google возвращает браузер в Supabase, а не в твоё приложение: OAuth-клиент, зарегистрированный в Google Cloud, — это Supabase-проект. Твой собственный /auth/callback получает уже второй, супабейсовский код, и живёт в другом списке — в Redirect URLs самого Supabase.

Где хранится code_verifier между кликом и обменом кода?

Обмен делает сервер, а localStorage серверу не виден — поэтому @supabase/ssr подменяет storage на cookie и специально обрабатывает ключ -code-verifier (cookies.js:263). В flow_state лежит challenge, а не verifier: сервер обязан хранить только необратимый хеш, иначе PKCE не имел бы смысла.

Почему обмен кода делает route handler, а не server action?

Server action вызывает твой код; сюда же браузер приезжает сам по 302 от Supabase — принять такую навигацию может route handler или страница. Читать и писать cookie server action умеет (serverSignIn ровно это и делает), а query-параметры видит любой серверный код — дело исключительно в том, кто инициирует запрос.

Что сломает /auth/callback именно в этом проекте?

localePrefix: "as-needed" заставляет next-intl переписывать непрефиксованные пути в /en/…, а роута /en/auth/callback нет — 404, и одноразовый код сгорает впустую. Query-параметры при рерайте сохраняются, cookie никто не удаляет; проблема ровно в подмене пути, поэтому auth нужно исключить из matcher.
